# codegen/ -- in-process hx P4 state-machine codegen (Phase 2-3+)

This directory holds the in-process P4 state-machine hx codegen for
mdxfind Phase 2-3 (and beyond). It is **distinct from `gpu/codegen/`**,
which is the rev1 offline-Python reference approach that the strategic
scoping rev2 (2026-05-20) superseded.

## Architecture (rev2)

- **In-process** P4 state-machine walker embedded directly in mdxfind.
- **Bytecode-driven**: hx specs are compiled-in C data tables
  (`hx_specs_data.c`, arriving in sub-phase 2a.2); each spec carries a
  small composition bytecode that the walker interprets to emit
  OpenCL or Metal kernel source on demand.
- **Specialized per invocation**: the walker bakes (-i / -n / -N / -r /
  salt regime) into the emitted source via a `struct hx_specialization`
  argument.
- **Hybrid hand-written / codegen**: a future `hx_override_table[]`
  short-circuits algorithms that resist codegen (bcrypt, scrypt,
  yescrypt, Argon2) to hand-written kernels.

## Sub-phase 2a.2 scope (current)

Walker skeleton rewritten around the production hx VM:
- `hx_spec.h` -- codegen-context types (backend, salt regime, iter shape,
  digest endianness, specialization). The invented 2a.1 bytecode is GONE.
- `hx_spec_entry.h` -- wrapper struct for the auto-generated
  `hx_specs_data[]` array.
- `hx_walker.h` / `hx_walker.c` -- state machine dispatched on the
  production 16-opcode `hx_opcode` enum from `../hx_vm.h`.
- `hx_emit.h` -- internal helper signatures (skeleton + per-opcode).
- `hx_emit_opencl.c` -- OpenCL emit helpers, minimum-viable per-opcode
  set (PUSH_VAR/PUSH_STR/PUSH_INT/STORE/CALL[md5]/CONCAT/HALT).
- `hx_emit_metal.c` -- Metal stubs with matching signatures (deferred
  to 2a.4).
- `hx_dump.c` -- env-flag-driven source dump.
- `hx_specs_data.c` -- AUTO-GENERATED by `tools/hx8_to_c` from
  `~/Documents/troff/mdxfind/hx.8`. Contains 994 pre-compiled
  `hx_program` structs (781 non-outlier, 210 outlier, 3 compile-fail).
  DO NOT check this file into RCS; it is regenerated on every make.

The walker consumes a real production `hx_program` directly. The
harness in `mdxfind.c` looks up an entry via `hx_specs_lookup(JOB_*)`
(default e1 MD5; override via `MDXFIND_HX_CODEGEN_JOB=N` env var) and
drives the walker against it. JIT-validated on Pascal GTX 1080 for e1
(simple), e31 (PUSH_VAR + CALL md5 + PUSH_VAR + CONCAT + CALL md5 +
HALT), e347 (same bytecode shape as e31 -- the hx.8 catalog quirk).

This is still harness-mode only -- not wired to the runtime dispatch

## Build-time tool

`tools/hx8_to_c` reads `hx.8` and emits `codegen/hx_specs_data.c`.
Compiles in `-DHX_STANDALONE -DHX_NO_MAIN` mode against the existing
hx library; pre-scans expressions to register stub function entries
for the long-tail hashpipe-only primitives (so `hx_compile_expr` never
hits its `exit(1)` path on unknown function). See
`tools/Makefile.frag` for the link rule.

## RCS discipline

`codegen/RCS/` holds per-file RCS history. Hand-authored `.c` and `.h`
files use the default `kv` keyword mode; the Revision and Log keyword
stanzas at the top of each file expand in-place on `ci -l` and provide
inline identity / history per `feedback_rcs_keyword_stanzas.md`.

This README file itself is checked in with `-ko` (no keyword expansion)
so that prose mentioning the keyword strings does not get rewritten by
RCS.
