# Rule Reference

mdxfind (via `-r` and `-R`) and [procrule](https://github.com/Cynosureprime/procrule) implement hashcat/JtR-compatible password mutation rules.

Rules are written one per line in a rule file. Each rule is a sequence of operations applied left to right. Multiple operations can be combined on a single line to create complex transformations.

Positions are encoded as `0`–`9` for positions 0–9, `A`–`Z` for positions 10–35, and `a`–`z` for positions 36–61. This allows rules to address characters up to position 61 in very long passwords.

## The Implicit No-Rule Pass

When `-r` (or `-R`) is active, mdxfind tests every word in the wordlist **as-is** before applying any rule. The unmodified word is always part of the candidate stream. This is intentional: the original input is part of the search space whether or not rules are supplied.

Concretely, with a wordlist of `[apple, banana]` and a rule file containing `[$1, $2]`, mdxfind generates six candidates per pass:

```
apple        (no-rule pass)
apple1       ($1)
apple2       ($2)
banana       (no-rule pass)
banana1      ($1)
banana2      ($2)
```

Per word, the candidate count is at most `1 + N_rules`. The leading `1` is the no-rule pass.
It is a ceiling and not an exact figure, because a rule whose output is bytewise identical to
its input is skipped — see [Redundant-rule skip](#redundant-rule-skip) below.

### Comparison with hashcat

hashcat's rule engine omits the no-rule pass; only rule-mutated outputs are tested. To reproduce mdxfind's coverage with hashcat, prepend the no-op rule `:` to the rule file. mdxfind, by contrast, treats the no-rule pass as a property of the search loop itself rather than a rule that can be omitted.

A practical consequence: the no-op rule `:` is structurally redundant in mdxfind. When mdxfind reports rule counts, the `:` rule is filtered out of the working set:

```
$ mdxfind -r best64.rule -f hashes.txt wordlist.txt
103 rules read from best64.rule
77 total rules in use
```

The 26-rule difference between "read" and "in use" includes comments, blank lines, the `:` rule, and any rules that failed to parse.

### Redundant-rule skip

Because the no-rule pass is guaranteed to fire, any rule whose output is bytewise identical to its input is redundant — the unmodified word has already been hashed. mdxfind detects this at rule-application time and skips the hash. The rule engine returns a distinct result for "output equals input" (`-2`) as well as for "rejected" (`-1`), and every call site drops both.

```
$ printf 'pass\n' > w.txt
$ printf 'l\n' > r.txt                      # 'l' does not change "pass"
$ mdxfind -m e1 -G none -r r.txt -f hashes.txt w.txt
1 rules read from r.txt
1 total rules in use
1.00 seconds hashing, 1 total hash calculations
```

One hash calculation, not two: the no-rule pass ran and `l` was skipped. Adding `u` to the same rule file raises the count to two, not three.

hashcat cannot perform this optimization because it has no guaranteed unmodified-input pass to defer to. procrule has always done the equivalent: it never emits a candidate equal to the word that produced it. Any published mdxfind candidate count that equals `words × rules` exactly was measured before this skip existed — see [Internal Rules vs External Pipeline](#internal-rules-vs-external-pipeline).

## Rules with Masks: Cross-Product

As of mdxfind rev 1.342, rules (`-r`, `-R`) and masks (`-n`, `-N`) compose as a full cross-product. Each rule output is combined with each mask value to form a candidate, and the candidate count per word is:

```
(1 + N_rules) × M_masks
```

The leading `1` is the implicit no-rule pass described above; it participates in the cross-product on equal footing with rule outputs. With 100 words, 5 rules, and the mask `?d` (10 values), the candidate count is `100 × 6 × 10 = 6,000`.

### Worked example

```
mdxfind -m e1 -r rules.txt -n '?d?d' -f hashes.txt wordlist.txt
```

For each word in `wordlist.txt`:

1. Apply the no-rule pass and each rule in `rules.txt` to produce `1 + N_rules` ruled bases.
2. For each ruled base, append every value of the mask `?d?d` (100 values, `00` through `99`).
3. Hash each `(ruled_base, mask_value)` candidate as MD5 (`-m e1`) and compare against `hashes.txt`.

If `rules.txt` contains 5 rules, each word produces `6 × 100 = 600` candidates.

### GPU and CPU paths

The cross-product semantics are identical on the GPU and CPU paths.

- **GPU path.** Each ruled base is dispatched to the GPU once. The kernel iterates all mask values per ruled base on-device, producing `M_masks` hash computations per dispatched base. This avoids round-tripping mask values through host memory and is the preferred path when an eligible GPU is available. The slab-format kernel handles the rules+masks dispatch.
- **CPU path.** The same `(rule × mask)` cross-product is generated by iterating masks within each rule pass. A per-thread `rule_base` stash preserves the rule-applied word across mask iterations, so the rule advance step does not need to re-apply the rule on each mask cycle. Throughput depends on the hash algorithm; for fast algorithms (MD5, SHA1) the GPU path is substantially faster when available.

The GPU and CPU paths must produce the same hit set for any given input. Validation runs compare hit sets and counts between `-G auto` (GPU eligible) and `-G none` (CPU only) on identical input. There are two documented exceptions, both about length: which words the GPU is offered, and how much output a rule may generate before the walker stops. See [The GPU and CPU rule engines](#the-gpu-and-cpu-rule-engines).

### Performance note

A 5,000-rule MD5 run on a single NVIDIA RTX 4070 Ti SUPER establishes the rules-only GPU baseline at approximately 401 MH/s. Workloads combining rules with short masks dispatch through the same packed kernel and inherit this throughput as a starting point; absolute numbers vary with rule complexity, base-word length distribution, and mask cardinality. See [BENCHMARK.md](BENCHMARK.md) for tracked configurations.

## Case Rules

| Rule | Description | Example |
|------|-------------|---------|
| `l` | Lowercase all characters | `PaSsWoRd` → `password` |
| `u` | Uppercase all characters | `password` → `PASSWORD` |
| `c` | Uppercase position 0, lowercase the rest | `password` → `Password` |
| `C` | Lowercase position 0, uppercase the rest | `Password` → `pASSWORD` |
| `t` | Toggle case of all characters | `PaSsWoRd` → `pAsSwOrD` |
| `TN` | Toggle case at position N | `password` → `pAssword` (T1) |
| `E` | Title case (capitalize after each space) | `hello world` → `Hello World` |
| `eX` | Title case with custom separator X | `hello-world` → `Hello-World` (e-) |
| `3NX` | Toggle case of first letter after the Nth occurrence of separator X | `foo.bar.baz` → `foo.Bar.baz` (30.) |

`c`, `C`, `E` and `eX` act on **position 0**, not on the first alphabetic character. If
position 0 is not a letter, nothing is capitalised there and the rest of the word is still
re-cased:

```
c   on !bang   → !bang      (not !Bang)
C   on !bang   → !BANG      (not !bANG)
E   on 9999Z999 → 9999z999
```

For `E` and `eX` the word start is positional too: the first character after a separator,
whether or not it is a letter. John and hashcat agree with each other here and mdxfind was
the outlier until this was corrected.

This matters most for candidates a rule has *already* made start with a non-letter, which is
easy to miss when reading a rule file: real examples from `HashMob.100k.rule` turn `@Bcdef`
into `@bcdef` and `:Password` into `:password`. Measured impact over 60,000 contest words:
0.272% of the unique candidate set.

`E` and `eX` keep an already-uppercase letter at a word start rather than re-casing it, so
`Hello1` stays `Hello1` and `abc Def` becomes `Abc Def`.

One residual John/hashcat disagreement: for `ea`, where the separator itself sits at
position 0, hashcat force-uppercases position 0 at the end of the pass and John does not.
`apple` under `ea` is `APple` in hashcat and `aPple` in John. **mdxfind follows John**, which
is also what it has always done.

`TN` with N at or past the end of the candidate is a no-op, now by an explicit bounds check
rather than incidentally. `3NX` counts occurrences from zero: `30.` acts after the first
`.`, `31.` after the second.

## Insertion and Deletion

| Rule | Description | Example |
|------|-------------|---------|
| `$X` | Append character X | `pass` → `pass1` ($1) |
| `^X` | Prepend character X | `pass` → `1pass` (^1) |
| `[` | Delete first character | `password` → `assword` |
| `[^X` | Overwrite the first character with X — an mdxfind extension, equivalent to `o0X` | `password` → `Qassword` ([^Q) |
| `]` | Delete last character | `password` → `passwor` |
| `DN` | Delete character at position N | `password` → `pasword` (D3) |
| `iNX` | Insert character X at position N | `password` → `pas-sword` (i3-) |
| `oNX` | Overwrite character at position N with X | `password` → `pas@word` (o3@) |
| `'N` | Truncate word at length N | `password` → `pass` ('4) |
| `xNM` | Extract M characters starting at position N, if the whole range fits | `password` → `swor` (x34) |
| `ONM` | Delete M characters starting at position N | `password` → `pasd` (O3 4) |

Out-of-range positions are not treated uniformly. Each case follows one of the two
references rather than being invented here, and which one is stated:

- `iNX` inserts at position N, and N *equal to* the current length appends — `i1a` on `a`
  gives `aa`. N beyond the length is a no-op. (John appends there too; hashcat no-ops. The
  references disagree, so mdxfind follows hashcat for the beyond-the-length case only.)
- `xNM` is a **no-op unless the whole range fits** — both `N` past the end and
  `N + M` past the end leave the candidate untouched, and it never extracts a partial run.
  This follows hashcat's `mangle_extract()`, which tests both conditions and returns
  unchanged. John does neither: it rejects an out-of-range start and extracts as much as is
  available when the count overruns. On `abc`, `x22` and `x23` give `abc` here and `c` in
  John; `x90` gives `abc` here and a rejection in John. On `password`, `x34` gives `swor` in
  both, `x74` gives `password` here and `d` in John.
  A zero count with an in-range start still empties the candidate in both engines — `x00`
  and `x30` yield the empty string, which mdxfind keeps (see below) and John rejects.
- `ONM` is the asymmetric twin: out of range it is a silent no-op, not a rejection. This
  matches John, which is also asymmetric here.
- `oNX` on a zero-length candidate with N = 0 appends X, so `'0 o0Q` yields `Q`. This is an
  mdxfind quirk with no counterpart in either reference.
- `'N`, `DN`, `zN`, `ZN`, `yN`, `YN` and `pN` are no-ops when the operand resolves to 0 or
  is past the end.

## Duplication

| Rule | Description | Example |
|------|-------------|---------|
| `d` | Duplicate entire word | `pass` → `passpass` |
| `f` | Reflect — append reversed copy | `abc` → `abccba` |
| `pN` | Append duplicated word N times | `ab` → `ababab` (p2) |
| `q` | Duplicate every character | `abc` → `aabbcc` |
| `zN` | Duplicate first character N times | `pass` → `pppass` (z2) |
| `ZN` | Duplicate last character N times | `pass` → `passss` (Z2) |
| `yN` | Duplicate first N characters, prepend them | `password` → `papassword` (y2) |
| `YN` | Duplicate last N characters, append them | `password` → `passwordrd` (Y2) |

## Rearrangement

| Rule | Description | Example |
|------|-------------|---------|
| `r` | Reverse the word | `password` → `drowssap` |
| `{` | Rotate left — move first character to end | `password` → `asswordp` |
| `}` | Rotate right — move last character to front | `password` → `dpasswor` |
| `k` | Swap first two characters | `password` → `apssword` |
| `K` | Swap last two characters | `password` → `passwodr` |
| `*NM` | Swap characters at positions N and M | `password` → `psasword` (*1 2) |

## Character Manipulation

| Rule | Description | Example |
|------|-------------|---------|
| `sXY` | Replace all occurrences of X with Y | `password` → `p@ssword` (sa@) |
| `@X` | Purge — remove all occurrences of X | `password` → `pssword` (@a) |
| `+N` | Increment ASCII value at position N | `password` → `qassword` (+0) |
| `-N` | Decrement ASCII value at position N | `password` → `oassword` (-0) |
| `.N` | Replace character at N with character at N+1 | `password` → `psssword` (.1) |
| `,N` | Replace character at N with character at N-1 | `password` → `ppssword` (,1) |
| `LN` | Bit-shift the byte at position N left one bit | `pass1` → `passb` (L4) |
| `RN` | Bit-shift the byte at position N right one bit | `password` → `8assword` (R0) |
| `BNX` | Add the byte value of X to the byte at position N, with unsigned wrap | `pass1` → `passb` (B41) |
| `vNX` | Insert character X after every N characters, including at the end | `password` → `pa-ss-wo-rd-` (v2-) |

`.N` is a no-op when there is no character at N+1, so `.8` on `abcdefghij` gives
`abcdefghjj` and `.9` leaves the word unchanged. `,N` is likewise a no-op at N = 0.
`+N`, `-N`, `LN`, `RN` and `BNX` are no-ops when N is at or past the end.

`BNX` tracks hashcat **master**, where it is `RULE_OP_MANGLE_CHR_ADD` in `src/rp_cpu.c`.
It is **not** in the hashcat 6.2.5 release and does not exist in John, so a rule file using
it will not run under either. hashcat's own example is `B50` on `hello0`, which yields
`hello` followed by a backtick (0x30 + 0x30 = 0x60). `procrule -u` refuses the verb
outright: the UTF-32 engine does not implement it.

## Memory

Memory rules allow saving and recalling the word state, enabling complex multi-step transformations.

| Rule | Description |
|------|-------------|
| `M` | Memorize current word state |
| `4` | Append memorized word |
| `6` | Prepend memorized word |
| `Q` | Reject word if it equals the memorized word (use after `M` to ensure the rule changed something) |
| `XNMI` | Insert M characters of the memorized word, starting at offset N within it, at position I of the current word |

Example: `Mc$1Q` — memorize original, capitalize, append "1", reject if unchanged. This ensures only words that were actually modified are emitted.

The whole family runs on the GPU. It was CPU-only until the rule walker buffer shrank to
2048 bytes, which made a second buffer of the same size affordable per thread; see
[The GPU and CPU rule engines](#the-gpu-and-cpu-rule-engines). `memlen` resets on every rule
application, so there is no cross-rule state for an independent work-item to reproduce.

All three `XNMI` operands are used. On `abcdef`:

```
MX034 → abcdabcef      offset 0, 3 chars, inserted at position 4
MX134 → abcdbcdef
MX234 → abcdcdeef
MX334 → abcddefef
```

**Out of range, `X` rejects the candidate rather than clamping** — this follows hashcat's
`mangle_insert_multi()`. It rejects on any of: no memory stored, insert position I past the
current length, offset N past the memorized length, N + M past the memorized length, M less
than 1, or a result too long for the buffer. John clamps instead, so `MX049` on `abcdef` is
`abcdefabcd` in John and a rejection here.

A known divergence from hashcat, deliberately not replicated: hashcat's implementation
memmoves its own memory buffer while reading it, so a second `X` in one rule sees shifted
memory. `MX134X134` on `abcdef` gives `abcdcdebcdef` in hashcat and `abcdbcdbcdef` here,
which is what John also gives.

## Rejection and Control

Rejection rules filter candidates based on conditions. If the condition is met, the candidate is rejected (not emitted).

| Rule | Description |
|------|-------------|
| `<N` | Reject unless the length is **less than** N (that is, reject when length >= N) |
| `>N` | Reject unless the length is **greater than** N (reject when length <= N) |
| `_N` | Reject unless the length **equals** N |
| `=NX` | Reject unless the character at position N is X |
| `%NX` | Reject unless X occurs **at least** N times |
| `!X` | Reject if word contains character X |
| `/X` | Reject if word does not contain character X |
| `(X` | Reject if first character is not X |
| `)X` | Reject if last character is not X |
| `:` | No-op. Compiles to an empty program and is dropped from the working set |
| `#` | **Comment.** A bare `#` — one standing where a verb is expected — comments out the rest of the line; nothing after it is examined. `c#$1` is "capitalize, then a comment". As a verb's *operand* it is ordinary data, so `$#` appends `#`, `@#` purges `#` and `sa#` substitutes `#`. A whole-line comment is just the degenerate case, with the `#` first. |

All three length tests read the **current** candidate length at the point the verb is
reached, not the length of the input word. `$a _5` keeps a four-character word, because by
then the candidate is five characters; `$a _4` rejects it. `d _8` keeps `pass`, `d _4`
rejects it.

A trailing comment needs no separator: `c#$1` and `c #$1` both compile to `c`. So if a rule file mangles less than expected, grep it for `#` — the verbs after one are commentary, and the rule loads and reports normally because nothing is wrong.

`<N`, `>N` and `_N` follow John, whose wording is unambiguous and whose rule engine will
actually run them. hashcat's own comments for `<` and `>` read the other way round; the
verbs are also ineligible for its GPU rule engine.

### A candidate a rule empties is kept

If a rule reduces a candidate to zero length, mdxfind **keeps it and carries on**. John
rejects the candidate at that point and abandons the rest of the rule. mdxfind follows
hashcat. This is long-standing mdxfind behaviour and is now a deliberate, ruled divergence
rather than an accident.

Two consequences worth knowing:

```
$ printf "'0\n" > r.txt                 # truncate to zero length
$ mdxfind -m e1 -G none -r r.txt -f hashes.txt words.txt
MD5x01 d41d8cd98f00b204e9800998ecf8427e:
```

The empty string is a real candidate and its MD5 is computed. And the rest of the rule still
runs, so `'0 $Z` yields `Z` where John yields nothing. The same applies to `@a` on the word
`a`, to `x00`, and to `]]` on a two-character word.

It is also the single cause of every remaining difference from John in the character-class
sweep below — 9 of 75 rules — so a John/mdxfind comparison that does not account for it will
look like a class bug and is not one.

`(X` and `)X` accept a zero-length candidate rather than rejecting it: with nothing there,
there is no first or last character to disagree with X.

`#` is not a run-time verb. The compiler stops at the first `#` in the line, so `c#$1`
applies `c` and never sees `$1`. It does not stop the remaining rules in the file.

## Character Classes

Nine verbs accept a **character class** in place of a literal character. There are two
syntaxes, and the prefix selects both the class table and which reference mdxfind is
matching:

| Syntax | Table | Classes | Complement |
|--------|-------|---------|------------|
| `?C` (unprefixed) | John's | `?l ?u ?d ?s ?v ?c ?w ?p ?a ?x ?o ?b ?y ?z` | yes — uppercase the letter |
| `~` + `?C` | hashcat's | `?l ?u ?d ?s ?h ?H` | no |

In John's table an uppercase class letter is the complement of the lowercase one, so `?D` is
"not a digit" and `@?D` on `pass1` leaves `1`. hashcat has no complement form.

| Class | Size | Members | Table |
|-------|------|---------|-------|
| `?l` | 26 | `a-z` | both |
| `?u` | 26 | `A-Z` | both |
| `?d` | 10 | `0-9` | both |
| `?s` | 33 | space and every printable non-alphanumeric | both |
| `?h` | 16 | `0-9a-f` | hashcat only |
| `?H` | 16 | `0-9A-F` | hashcat only |
| `?v` | 10 | `AEIOUaeiou` | John only |
| `?c` | 42 | consonants, both cases | John only |
| `?w` | 2 | space and tab | John only |
| `?p` | 9 | ``!"',.:;?`` and the backtick | John only |
| `?a` | 52 | `a-zA-Z` | John only |
| `?x` | 62 | `a-zA-Z0-9` | John only |
| `?o` | 47 | control bytes: `0x01`–`0x08`, `0x0a`–`0x1f`, `0x7f`, and the C1 controls John lists. Excludes NUL and tab | John only |
| `?b` | 128 | `0x80`–`0xff` | John only |
| `?y`, `?z` | 256 | every byte | John only |

Sizes and membership above were read back out of the engine, not copied from a header.

### The nine verbs

Each takes a class in either syntax:

| Literal form | Class form | Meaning with a class |
|--------------|------------|----------------------|
| `sXY` | `s?CY` | replace every character of class C with Y |
| `@X` | `@?C` | purge every character of class C |
| `eX` | `e?C` | title case, treating class C as the separator |
| `!X` | `!?C` | reject if the word contains any character of class C |
| `/X` | `/?C` | reject unless the word contains one |
| `(X` | `(?C` | reject unless the first character is in class C |
| `)X` | `)?C` | reject unless the last character is in class C |
| `=NX` | `=N?C` | reject unless the character at position N is in class C |
| `%NX` | `%N?C` | reject unless at least N characters are in class C |

```
s?dX   on Pass1   → PassX
@?d    on Pass1   → Pass
@?D    on pass1   → 1            complement: purge everything that is not a digit
~@?H   on Pass1 x → Pass x       hashcat table: 1 is an uppercase hex digit
(?u $Z on Pass1   → Pass1Z       first character is uppercase, so kept
(?u $Z on pass1   → (rejected)
```

### `??` is the literal-`?` escape — in both syntaxes

Because `?` now introduces a class, a rule that wants to operate on a **literal** question
mark must double it: `@??` purges `?`, and `s??!` replaces `?` with `!`. This is John's
escape, and hashcat has it too. The doubled form means the same thing in the byte engine and
under `procrule -u`, so a rule file fixed this way works under both.

**This breaks existing rule files.** Eight lines across the rule files shipped with mdxfind
no longer load — four in `HashMob.100k.rule`, three in `d3ad0ne.rule`, one in
`generated.rule` — every one of them because it wrote `@?` or `s?` intending a literal `?`.
All eight are rules John also rejects, with the same complaint. The fix is mechanical:

```
@?     →  @??
s?!    →  s??!
```

A rule that names no class is refused at load time and dropped, with the caret pointing at
the operand, so this fails loudly rather than silently:

```
  Rule: @?0
          ^
  Error: Invalid character class for command '@'
Invalid rule line. Ignored.: @?0
```

### Three decisions worth stating as decisions

- **`?s` is hashcat's `class_sym()` in both tables** — space, `!`–`/`, `:`–`@`, `[`–`` ` ``
  and `{`–`~`. John's `?s` is narrower. Run `@?s` over the printable ASCII range and
  mdxfind leaves exactly `0-9A-Za-z`, where John additionally leaves space and
  ``!"',.:;?`` and the backtick. This is a deliberate choice, not an oversight.
- **John's user classes `?0`–`?9` are not implemented.** They are defined per rule file in
  John's config; mdxfind has no equivalent and refuses them. Undefined, John refuses them
  too.
- **Hex classes exist only in the hashcat table.** This is what forces the two tables apart.
  Under `~`, `?H` is uppercase hex; unprefixed, an uppercase class letter means "not the
  lowercase class", so a John-table `?h` would make `?H` mean "not lower hex" — the same
  two characters meaning two different things. mdxfind keeps hex out of the John table
  entirely, so unprefixed `?h` and `?H` name no class and are refused. **John refuses
  `?h` and `?H` as well**, so nothing is lost. John resolves the same collision differently,
  by disabling inline `?C` for a whole file with its `!! hashcat logic ON` directive; `~` is
  per-rule and composes better.

### `e?C` and `~e?C` are different algorithms

This is the one verb where the two references do not merely differ in their class tables but
compute different results, so mdxfind carries both as separate operations:

- **`e?C` (John).** Title case with a class member acting as the separator. The separator
  itself is left as it stands.
- **`~e?C` (hashcat).** Lowercase every position, then uppercase position 0 and every
  position whose *predecessor* is in the class — judged on the original bytes, before any
  modification. The separator is case-normalised along with everything else.

```
e?u  on aBcDe → ABCDE      B and D are separators; a, c, e start words
~e?u on aBcDe → AbCdE      everything lowercased, then 0, 2 and 4 uppercased
```

Over eight adversarial words, mdxfind's `e?u` matched John on all eight, and the two forms
disagreed with each other on five. Use `~e?C` only when reproducing a hashcat run.

### Classes run on the GPU

All ten class opcodes are implemented in all six rules kernels, sharing one 480-byte
membership table in the constant address space so the six cannot drift. `=NX` and `%NX`
became GPU-eligible in the same change. A class rule no longer forces a mixed GPU/CPU
partition, which matters beyond throughput: a partitioned run has to union two result sets.
See [The GPU and CPU rule engines](#the-gpu-and-cpu-rule-engines).

Classes are **not** implemented in the UTF-32 engine, but a class rule cannot mean two
different things there: `procrule -u` refuses every class form at load time, naming the rule.
The `??` escape is the exception and works identically in both engines, so the `@?` → `@??`
migration above is safe under `-u` as well. See `man 7 rules32`.

### Validation

Against hashcat's own engine, 21 of 21 class rules agree. Against John, 66 of 75, with all
nine differences being the ruled empty-candidate policy described above and none being a
class defect.

## The GPU and CPU Rule Engines

One rule set, two engines. Which engine handles a given word is decided per word, and the
two are not interchangeable at the extremes. What follows is policy, not implementation
detail — it changes what a run produces.

### The input word is gated at 1024 bytes

A word of 1 to 1024 bytes is eligible for the GPU rule engine. A longer word goes to the
CPU, which applies every rule to it there. The gate is on the **input word only**.

Nothing is checked about what a rule *produces*. That is deliberate rather than an
oversight: rule output cannot be bounded in principle, because for any limit, on either
engine, a rule that overflows it can be written. So a limit is set arbitrarily. A rule that
reaches it does what it can, stops, and whatever has been generated becomes the candidate —
no error, no warning, no status indication.

The GPU walker buffer is 2048 bytes, twice the input gate, with a usable limit of 2033. The
15 bytes of slack cover a terminating NUL and the `n+1` boundary conditions in the per-verb
bounds checks. On the CPU the equivalent ceiling is `MAXLINE`, which is far larger.

### The two engines can therefore diverge

A rule whose output passes 2033 bytes truncates on the GPU where it would not on the CPU, so
the two paths generate different candidates for that word. **This is designed behaviour, not
a defect.** There is no retry to the CPU when a rule line exceeds the GPU limit, and no
fallback that would mask the difference.

If you need CPU-exact output, run with `-G none`.

### Both limits are compile-time

The 1024-byte gate and the 2048-byte buffer are compile-time constants
(`GPU_RULES_MAX_INPUT_LEN` and `GPU_RULES_WALKER_BUF_ELEMS` in `gpujob.h`). The buffer size
is injected into every GPU program from that one definition, so a kernel and its host cannot
disagree about it. **There are no environment variables that change either value**, and
nothing in the run-time interface is tunable here. Changing them means rebuilding.

### Three verbs remain CPU-only

Everything else in the rule language runs on the GPU — the character classes in both
syntaxes, `=NX` and `%NX`, and the whole memory family `M 4 6 Q X`, which was CPU-only until
the walker buffer shrank enough to afford a second one per thread.

| Verb | Why |
|------|-----|
| `S` | mdxfind-specific; pending a restructure of its case table |
| `vNC` | Divide-insert |
| Control-B (`0x02`) | Base64-encode the candidate; out of GPU scope by ruling |

A rule using one of these routes to the CPU list while the rest of the rule set still runs on
the GPU. The reported hit set is the union of the two partitions and is the same either way;
only throughput differs.

`#` is **not** a fourth. It never reaches the bytecode: the rule compiler stops at the first
`#` in a line, so `c#$1` compiles to `c` and the `$1` is never seen. A line that *begins*
with `#` therefore compiles to nothing and is dropped at load, which is exactly the comment
convention every rule file relies on. `#` cannot be used to force a rule onto the CPU.

## Combining Rules

Multiple operations on a single line are applied left to right. This allows powerful combinations:

| Rule | Effect | Example with "password" |
|------|--------|------------------------|
| `c$1` | Capitalize + append 1 | `Password1` |
| `u$!$!` | Uppercase + append !! | `PASSWORD!!` |
| `sa@so0` | a→@ and o→0 (leetspeak) | `p@ssw0rd` |
| `^!c` | Prepend ! + capitalize | `!Password` |
| `r$1` | Reverse + append 1 | `drowssap1` |
| `d'8` | Duplicate + truncate to 8 | `password` (passpass → passp... truncated) |
| `Mc$1Q` | Capitalize + append 1 (only if changed) | `Password1` (rejects if already capitalized with 1) |

## Using Rules with mdxfind

```bash
# Apply rules from a file (concatenated)
mdxfind -r rules.txt -f hashes.txt wordlist.txt

# Apply multiple rule files (concatenated — rules are additive)
mdxfind -r best64.rule -r toggles.rule -f hashes.txt wordlist.txt

# Apply multiple rule files (dot-product — every combination)
mdxfind -R transforms.rule -R suffixes.rule -f hashes.txt wordlist.txt

# Show which rules were most effective
mdxfind -r rules.txt -Z -f hashes.txt wordlist.txt
```

See [EXAMPLES.md](EXAMPLES.md) for detailed examples with sample output.

## How mdxfind Processes Rules

### Compilation

When mdxfind reads a rule file, it goes through three phases:

1. **Parse** — each line is read and comments (lines starting with `#`) and blank lines are discarded.
2. **Validate** — each rule is compiled and then test-applied to the probe word `Password`. A rule with a malformed or missing operand, or one truncated mid-verb, is reported on stderr with its file and line number and dropped:

   ```
   Invalid position ! in rules
   Rule file rbad.txt: bad line 2
   ```

3. **Compile** — valid rules are converted into an internal bytecode format for fast application during the search loop. This avoids re-parsing the rule string for every candidate.

An unassigned verb letter is a different case, and a quieter one. A byte that names no verb
is **silently ignored**, with no diagnostic, and the rest of the rule still runs: `W$Z` on
`password` gives `passwordZ`. So a hashcat rule file containing verbs mdxfind does not
implement will not be rejected — it will run with those verbs elided, which is not the same
attack. Check an unfamiliar rule file with `procrule` before trusting a zero result from it.

Rule diagnostics are emitted **at load time only**. Nothing is reported at run time: a rule
that rejects a candidate, or produces output identical to its input, is silently skipped for
that word. This matches John and hashcat, and is deliberate — a per-candidate diagnostic on
a billion-candidate run is not usable output.

```
$ mdxfind -r best64.rule -f hashes.txt wordlist.txt
103 rules read from best64.rule
77 total rules in use
```

In this example, best64.rule has 103 lines. After removing comments, blank lines, and the no-op `:` rule (which reproduces the original word and is always tried implicitly), 77 rules remain.

### SIMD Rule Batching

For certain algorithms — notably MD5 — mdxfind can apply multiple rules to the same input word and compute the hashes in parallel using SIMD instructions. On x86_64, the MD5 implementation processes 4 candidates simultaneously in 128-bit SSE registers. This means that applying 4 rules costs approximately the same as computing a single MD5 hash.

This dramatically reduces the cost of rules. Here is a real benchmark using 1 million MD5 hashes, 13.5 million candidate words, and the best64 rule set (77 effective rules):

```
$ mdxfind -f 1m.txt 10m.pass                          # no rules
13,484,773 lines processed
1.00 seconds hashing, 13,484,773 total hash calculations
13.45M hashes per second
16,898 MD5x01 hashes found

$ mdxfind -r best64.rule -f 1m.txt 10m.pass           # with 77 rules
103 rules read from best64.rule
77 total rules in use
13,484,773 lines processed
1,038,192,924 total rule-generated passwords tested
53.22 seconds hashing, 1,038,192,924 total hash calculations
19.51M hashes per second
77,093 MD5x01 hashes found
```

**Analysis:**

| | No rules | With 77 rules |
|---|---|---|
| Candidates tested | 13.5M | 1,038M (77x) |
| Time | 1.0s | 53.2s |
| Throughput | 13.5M/s | 19.5M/s |
| Hashes found | 16,898 | 77,093 |

Without SIMD batching, 77 rules would take 77 × 1.0s = **77 seconds**. The actual time is **53 seconds** — a 1.45x speedup from the 4-wide SIMD rule batching. The effective throughput of 19.5M/s (higher than the no-rule 13.5M/s) reflects the amortization of per-word overhead across multiple rule applications.

The 77,093 hashes found (vs 16,898 without rules) show the dramatic improvement in coverage: 4.6x more hashes solved by trying common password mutations.

### Internal Rules vs External Pipeline

For comparison, the same candidates can be generated externally using procrule and piped into mdxfind. Since procrule suppresses rules that don't change the word, we also pass the original wordlist to ensure identical coverage:

```
$ procrule -r best64.rule 10m.pass | mdxfind -f 1m.txt stdin 10m.pass
948,460,875 lines processed
32.12 seconds hashing, 948,460,875 total hash calculations
29.53M hashes per second
77,093 MD5x01 hashes found
```

| Approach | Candidates | Wall time | CPU time | Throughput | Hashes found |
|----------|-----------|-----------|----------|------------|-------------|
| Internal rules (`-r`) | 1,038M | 53s | 1m32s | 19.5M/s | 77,093 |
| External pipe (procrule) | 948M | 32s | 4m56s | 29.5M/s | 77,093 |

Several things to note:

- **Candidate count differs.** procrule suppresses a candidate equal to the word that produced
  it (e.g. `l` on an already-lowercase word), generating 948M. mdxfind reported 1,038M — about
  9% more work. Neither tool deduplicates *across* rules, so two rules converging on the same
  candidate are hashed twice on both paths.
  **These figures predate the [redundant-rule skip](#redundant-rule-skip).** 1,038,192,924 is
  only 134,597 short of 13,484,773 × 77, so the mdxfind build measured here was still hashing
  no-op rule output. On a current build the two counts converge; the run needs re-measuring.
- **Internal rules use 3.2x less total CPU** despite processing more candidates. The SIMD rule batching and avoidance of I/O overhead between processes make internal rules far more CPU-efficient.
- **External pipe is faster in wall time** on an idle multi-core system because procrule and mdxfind run on separate cores in parallel, and mdxfind's no-rule inner loop has higher per-candidate throughput (no rule bytecode interpretation overhead).

Both approaches find the same 77,093 hashes. Use internal rules (`-r`) when CPU efficiency matters or cores are limited; use procrule when you need the candidate list for other tools (hashcat, etc.) or when wall-clock time on an idle multi-core system is the priority.
