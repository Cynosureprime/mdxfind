# mdxfind — Supported Hash Types

Every hash type mdxfind supports, with its internal `-m eNNN` index, the
equivalent hashcat `-m` mode(s) where one exists, and a worked example in
mdxfind's own output format.

**1001 types.** 998 carry a verified example; the remaining 3 are evaluation instruments or a parsing wrapper for which no example is possible (see [Types without a published example](#types-without-a-published-example)).

Some types have a document of their own. `e1000` (7ZIP) is one: see
[SEVENZIP.md](SEVENZIP.md) for the hash format, the verification tiers, the
support tools, and the silent false negatives that affect other 7-Zip crackers.

Examples are the literal line mdxfind prints on a crack:

```
TYPE hash[:salt][:user]:password
```

Every example was generated by mdxfind and then independently confirmed by
`hashpipe`, the reference implementation. Salts and usernames are realistic
placeholders (`Xk7Qm2Rz`, `jsmith`) except where a type embeds its own salt,
in which case the example carries that type's native salt format.

The password is `password123` throughout, with two exceptions the algorithms
themselves impose: the LM family upper-cases it (`PASSWORD123`), and the
DES-crypt family truncates at 8 characters (`password`) — a longer password
there would produce an identical hash and make the example misleading.

A few examples use a password other than `password123` — the capitalising
types (`MD5CAP`, `SHA1SHA256CAP`, `SHA1MD5UC1LC` and relatives) only differ
from their base type when the intermediate digest actually contains a letter
in the position being capitalised. With `password123` the cap is a no-op and
the example would be indistinguishable from plain MD5, so a password was
chosen whose digest capitalises meaningfully.

Those types also emit **many** digests per candidate rather than one: mdxfind
walks every position it could capitalise and checks each, reporting the
position or iteration in the salt field where one applies. The example given
is the first such variant, which is the one `hashpipe` computes.

Rows marked **†** are iteration-2 values and need `-i 2` to crack. These are
types that differ from a base type only in what is fed back *between*
iterations (the `UC` and `RAW` families), so at iteration 1 they emit a value
byte-identical to their base type and no distinguishing example exists.

```sh
mdxfind -M eNNN -S salt.txt -U user.txt -i 1 -f /dev/null -z pw.txt
```

## Types without a published example

Three types are excluded from the table above -- two are built-in evaluation
instruments and one is a parsing wrapper, so no example is possible for them:

- **e425 NULL** performs no hashing. It zero-fills a 16-byte buffer, copies the
  first 16 bytes of the candidate into it and compares that directly, so it
  matches only list entries that literally are their own plaintext. Any
  "cracks" it produces are that passthrough, not an algorithm.
- **e426 PARALLEL** computes nothing at all; it only advances the hash counter,
  and exists for throughput measurement.
- **e435 MD5SPECAM** is a parsing wrapper that splits the candidate on `:` and
  delegates to MD5AM and MD5AM2, so it has no value of its own.

**e432 MD5AM** and **e433 MD5AM2** were written for a single breach corpus and
are used nowhere else. Their examples above are synthetic -- a placeholder user
on a reserved `example.com` address, with the house password -- and are drawn
from no real record. The salt field carries the account identifier: the user
name alone for MD5AM, and `user:email` for MD5AM2.

### Notes on particular examples

**e732 SHA1UTF7** cannot use the house password unmodified. UTF-7 leaves
printable ASCII unchanged, so for a pure-ASCII password the type degenerates to
plain SHA-1 and mdxfind deliberately emits nothing. The example appends `+`,
which is the UTF-7 shift character and must be escaped as `+-`. Passwords with
non-ASCII characters are the real use case, e.g. `Pässwörd123`
encodes to `P+AOQ-ssw+APY-rd123`.

**e770 SHA1BASE64CUSTBASE64MD5** emits four candidates per password. The
example is variant 1, which is the form observed in real corpora. Despite the
`CUST` in the name the base64 alphabet is standard RFC 4648.

**e990 WPA-PMK** takes a 32-byte PMK as the candidate, given as 64 hex
characters -- it does not run PBKDF2 itself. The PMK in the example is
`pbkdf2_sha1("password123", "hashcat-essid", 4096, 32)`, so it corresponds to
the house password on the ESSID used in the salt.
